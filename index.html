AI security research, grounded in standards

Casey Gager is an independent security researcher focused on non-human identity, agentic AI security, and runtime authorization. This site collects original research on the protocols, standards, and frameworks that will define how AI agents operate in production systems.

The work here is not vendor advocacy. It starts with standards bodies, threat models, and first principles — then asks what those mean for systems that act autonomously at scale.

Explainer

SPIFFE, SPIRE, and Workload Identity

Most identity systems were designed for humans. They assume a principal that can authenticate with a password, accept a push notification, or click a link. AI agents break this assumption. A model running inside a container on a Kubernetes cluster cannot enroll in MFA. It does not have a browser session. The question of how to establish trustworthy, verifiable identity for non-human workloads is one of the foundational problems in agentic AI security — and SPIFFE is the standard that answers it.

What SPIFFE is

SPIFFE stands for Secure Production Identity Framework For Everyone. It is a CNCF-graduated standard, not a product. SPIFFE defines a common vocabulary and set of specifications for issuing cryptographic identities to workloads running in dynamic, heterogeneous infrastructure. The goal is to give any process — a container, a VM, a serverless function, an AI agent — a verifiable identity that does not depend on network location, static secrets, or manual provisioning.

The identity itself is expressed as a SPIFFE ID: a URI following the format spiffe://trust-domain/path. The trust domain is the administrative boundary — analogous to a DNS zone but for identity issuance. The path encodes the workload's location within that domain.

# Examples of SPIFFE IDs
spiffe://prod.example.com/agent/payment-processor
spiffe://research.internal/model/inference-worker
spiffe://ai-platform.org/orchestrator/task-router

SPIFFE IDs appear inside SVIDs — SPIFFE Verifiable Identity Documents. There are two SVID formats, and they serve different purposes.

SVIDs: X.509 vs JWT

An X.509-SVID embeds the SPIFFE ID in the Subject Alternative Name field of a standard X.509 certificate. The private key stays on the workload; the certificate is the proof of identity. X.509-SVIDs are the right choice for service-to-service mTLS, where both sides authenticate each other at the transport layer. Because X.509 certificates are well-understood by TLS stacks, X.509-SVIDs integrate cleanly with existing infrastructure.

A JWT-SVID is a signed JSON Web Token carrying the SPIFFE ID as the sub claim. JWT-SVIDs are short-lived bearer tokens useful when transport-layer mTLS is not available or practical — cross-layer authentication, HTTP-based APIs, or systems where the identity needs to traverse a service mesh boundary. The tradeoff is that JWTs are bearer tokens: possession equals identity, so short expiry and strict audience binding are essential.

When to use which

Use X.509-SVIDs when you control both ends of a connection and can enforce mTLS. Use JWT-SVIDs when you need to pass identity through an application layer — an API gateway, an event bus, or a cross-cluster boundary where TLS termination happens before your service sees the request.

What SPIRE is

SPIRE (the SPIFFE Runtime Environment) is the reference implementation of SPIFFE. Where SPIFFE defines the standards, SPIRE implements them. SPIRE has two components: a SPIRE Server and SPIRE Agents that run on each node in your infrastructure.

The SPIRE Server is the certificate authority for a trust domain. It issues SVIDs, manages signing keys, and maintains the registration entries that map workload attributes to SPIFFE IDs. The SPIRE Agent runs on each node and handles workload attestation locally — it contacts the server on behalf of workloads, fetches their SVIDs, and exposes them via a local Workload API socket.

Workload attestation is the mechanism that makes this trustworthy. When a workload requests its SVID, the agent does not simply hand over credentials. It interrogates the workload using node-specific attestors — examining kernel metadata, cgroup membership, Kubernetes pod annotations, or platform attestation APIs. The server also performs node attestation when agents register, confirming that the node itself is what it claims to be. The result is identity that is derived from verifiable infrastructure properties, not from a secret the workload was handed at boot.

Trust domains and federation

A trust domain is the boundary within which a single SPIRE Server (or cluster of servers) is authoritative. Within a trust domain, SVIDs are automatically trusted. Across trust domains — different environments, different organizations, different cloud accounts — you need federation.

SPIFFE federation works by exchanging trust bundles: the set of root certificates that a trust domain uses to sign its SVIDs. If Trust Domain A trusts Trust Domain B's bundle, then B's SVIDs are valid in A's systems. Federation can be configured statically or via the SPIFFE Federation endpoint, which lets trust bundles refresh automatically as signing keys rotate.

Why this matters at scale

In a multi-cloud or multi-team AI system, federation is the mechanism that lets an agent provisioned in one environment call a service in another without static credentials crossing the boundary. The identity proof travels with the workload rather than being managed out-of-band.

Why this matters for agentic AI

AI agents introduce a new class of non-human principal. They are not service accounts tied to a specific server. They may be instantiated dynamically, run in ephemeral containers, spawn subagents, and act across multiple trust domains in the course of a single task. The identity model that most organizations use for service accounts — static credentials stored in a secrets manager — was not designed for this pattern. Static credentials do not automatically expire when an agent task completes. They do not carry proof of what infrastructure context the agent is running in. And they do not compose well when one agent spawns another.

SPIFFE addresses all three problems. SVIDs are short-lived and automatically rotated by SPIRE. They are derived from attestable infrastructure properties, so they carry proof of context. And because SPIFFE IDs are hierarchically structured URIs, they can encode agent lineage — an orchestrator's spawned subagent can carry an SPIFFE ID that encodes its relationship to the parent.

Connection to DIRA

SPIFFE answers the question who is this workload? It provides cryptographic, attestable identity at the infrastructure layer. DIRA asks the next question: given who this agent is, what is it actually trying to accomplish right now? SPIFFE establishes the subject. DIRA evaluates the intent. Together they form the foundation of a runtime authorization model that can keep pace with agentic AI behavior.

The practical implication is that any serious non-human identity architecture for AI agents should treat SPIFFE/SPIRE not as an optional hardening layer but as the baseline identity substrate — the thing everything else builds on. Vendor-specific agent identity solutions are proliferating, but they are not interoperable and they do not compose across trust domains. SPIFFE is the standard that makes composition possible.
